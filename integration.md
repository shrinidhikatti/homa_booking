# Student & Course Management System — Integration Plan

Source system of record: **Homa Booking** (React + Firebase/Firestore + Cloud Functions) — admission, payment, notes, courier, staff roles.
Course system of record: **VM Joshi LMS** (Frappe LMS v2.46.0 on Frappe v15, AWS-hosted) — courses, batches, quizzes, certificates, live classes.
Link key: **Student ID** (`AVJ-YYYY-NNN`, already generated by `studentFeeService.js`).

Full 6-phase plan below, matching the phase structure from the master requirement doc. Each phase should be tested and approved before the next one starts.

| Phase | Name | Nature of work |
|---|---|---|
| 1 | Foundation | New build |
| 2 | LMS Integration | Mostly integration (Frappe already has the core doctypes) |
| 3 | Notes & Courier | New build |
| 4 | Academic (progress, attendance, doubts, live sessions) | Mixed — progress/live-class sync is integration; attendance + doubt system are new builds |
| 5 | Exams & Certificate | Mostly integration (Frappe already has Quiz/Certificate doctypes) |
| 6 | Automation & Reporting | New build |

## PHASE 1 — Foundation

### 1. Workflow
```
Admission Form (enhanced)
        ↓
Student record created in Firestore (status: Payment Pending)
        ↓
Staff records payment (mode, transaction ID, amount)
        ↓
Payment status updates: Pending → Verification → Paid
        ↓
Once "Paid" (or partial paid per institute policy) → student unlocked for Phase 2 (LMS provisioning)
```

Staff access is gated by role from the moment they log in — this must exist before any other phase, since Notes/Accounts/LMS/Faculty screens all depend on it.

### 2. What already exists (no rebuild needed)
- `src/services/studentFeeService.js`: student CRUD, auto Student ID (`AVJ-YYYY-NNN`), batches collection, payments subcollection with receipt numbers and running paid/pending totals.
- `src/components/StudentFeeTab.js`: admission form, payment recording UI, batch management UI.
- Firebase Auth is already used for admin login (single account) — needs to become multi-role.

### 3. New database structure (Firestore)

| address, city, state, pincode | string | new |

**`staffUsers` (new collection):**

### 4. Features included
- Enhanced admission form: photo upload (Firebase Storage), DOB, email, full address, courier address, payment mode + transaction ID capture.
- Payment status pipeline (Pending → Verification → Paid → Failed/Refund) replacing the current implicit "paid in full or not" model.

### 5. What gets automated

- Confirm payment modes to support (Cash / UPI / Bank Transfer / Card / Cheque?).
- Decide if "courier address" is a separate field or "same as home address" checkbox.

### 7. Estimated timeline
**2–3 weeks.**

## PHASE 2 — LMS Integration (Frappe LMS)

### 1. Workflow
```
Student marked "Paid" in Homa Booking
        ↓
Cloud Function fires (Firestore trigger on students/{id} status change)
        ↓
Calls Frappe REST API:
   1. Create/find User (by email) in Frappe
   2. Set custom_student_code = Student ID on User
   3. Create LMS Batch Enrollment (assign batch)
   4. Create LMS Enrollment (assign course)
        ↓
lmsStatus: Account Pending → Created → Activated
        ↓
Welcome/login message sent via MSG91 WhatsApp (existing sendWhatsApp Cloud Function, extended with new template)
        ↓
Student dashboard in Homa Booking shows LMS status; periodic pull-back syncs progress/quiz/certificate data from Frappe into Firestore for the Master Student Profile
```

### 2. What already exists in Frappe LMS (confirmed by reading the deployed app — no code changed)
| Capability | Frappe LMS doctype / API |
|---|---|
| User account | `User` (core Frappe) |
| Course enrollment | `LMS Enrollment` |
| Batch enrollment | `LMS Batch Enrollment` |
| Course progress | `LMS Course Progress`, `get_lesson_completion_stats()`, `get_heatmap_data()` |
| Quizzes/exams | `LMS Quiz`, `LMS Quiz Submission` (score, percentage, passing_percentage) |
| Assignments | `LMS Assignment Submission` (status, evaluator, comments) |
| Certificates | `LMS Certificate` (member + course + batch + issue/expiry date) |
| Live classes | `LMS Live Class` + Zoom integration, `LMS Live Class Participant` (real joined_at/left_at) |

None of the above needs to be built — only **connected**.

### 3. New pieces required
- **Frappe side (config only, no code):** add Custom Field `User.custom_student_code` via Customize Form, so every Frappe user carries the Homa Booking Student ID. Requires Frappe admin/API-key access on the LMS instance.
- **Firebase side (new code):**
  - `frappeService.js` — REST client wrapping Frappe's `/api/resource/*` endpoints with API key/secret (stored in Firestore settings, same pattern as `msg91AuthKey`).
  - Cloud Function `provisionLmsAccount` — triggered on payment-verified, does the create-User → enroll-batch → enroll-course sequence.
  - Cloud Function `syncLmsProgress` — scheduled (like `sendDailyReminders`), pulls progress/quiz/certificate status per active student and writes into `students/{id}.lms` subfields.
  - New WhatsApp template for "LMS account activated / here are your login details."

### 4. Database structure additions

**`students/{id}.lms` (new nested object):**
| Field | Type | Notes |
|---|---|---|
| status | string | `not_started` \| `account_pending` \| `created` \| `activated` |
| frappeUser | string | Frappe User email (join key) |
| enrolledCourse | string | Frappe LMS Course name |
| enrolledBatch | string | Frappe LMS Batch name |
| progressPercent | number | synced from Frappe |
| lastLogin | timestamp | synced from Frappe |
| certificates | array | synced from `LMS Certificate` |

### 5. What gets automated
- LMS account creation + course/batch assignment — fully automatic on payment verification, zero manual data entry into Frappe.
- Welcome/login WhatsApp message — automatic.
- Progress/certificate sync into the Master Student Profile — automatic, scheduled.

### 6. What we need from you before starting
- **Blocking:** confirm Frappe API key/secret can be issued for the LMS instance (Administrator access or a dedicated integration user with API access to User/Enrollment/Batch/Certificate doctypes).
- Confirm whether login credentials should be auto-generated passwords (sent via WhatsApp) or a password-reset-link flow (more secure, standard Frappe behavior).
- Fix MSG91 billing (currently inactive — see earlier finding) since Phase 2's welcome message depends on it.

### 7. Estimated timeline
**2–4 weeks**, contingent on Frappe API access being granted promptly. If API access is delayed, this phase blocks entirely — recommend requesting it now, in parallel with Phase 1 build.

## PHASE 3 — Notes & Courier Management

### 1. Workflow
```
Student marked "Paid" + notesRequired = true
        ↓
Notes order auto-created (status: Pending)
        ↓
Staff generates a printing batch list (e.g. "PRINTING BATCH – 12 AUGUST")
        ↓
Printed ✅ → Quality Check → Packed
        ↓
Dispatched (courier company + tracking number entered) → In Transit → Delivered
        ↓
Status updates pushed to student via WhatsApp at key steps (Notes Ready / Dispatched)
```

### 2. New database structure

**`notesOrders` (new collection):**
| Field | Type | Notes |
|---|---|---|
| studentId | string | Student ID (link key) |
| studentName, course, batch | string | denormalized for list views |
| status | string | `pending` \| `printing` \| `qc` \| `packed` \| `dispatched` \| `in_transit` \| `delivered` |
| courierCompany | string | |
| trackingNumber | string | |
| dispatchDate, deliveredDate | timestamp | |
| courierAddress | string | pulled from `students/{id}.courierAddress` at creation time |
| qcCheckedBy, qcCheckedAt | string/timestamp | staff accountability |
| packedBy | string | |
| remarks | string | |

### 3. Features included
- Printing batch list generator, filterable/exportable by date.
- QC checklist screen (student ID match, course/module match, address match, packaging check) before status can move to "Ready for Dispatch."
- Courier entry form (company, tracking number, dispatch date).
- Status timeline shown on the Master Student Profile.
- Student-facing tracking visibility via WhatsApp status messages (no separate student portal needed unless Phase 4 builds one).

### 4. What gets automated
- `notesOrders` document auto-created when a student's payment is verified **and** `notesRequired = true` (Cloud Function trigger, same pattern as Phase 2's LMS provisioning).
- WhatsApp notification fired automatically on "Notes Ready" and "Dispatched" status changes.
- Tracking-number lookup: **only if** the courier partner has a public tracking API (see below) — otherwise dispatch status stays a manual staff update.

### 5. What we need from you before starting
- Which courier company/companies do you use? Delhivery, DTDC, India Post, Blue Dart, and a few others expose tracking APIs — if you use one of these, live "In Transit" updates can be automated. If it's a local/informal courier, tracking will be manual staff entry only.
- Who performs QC — confirm this sits with the `notes_team` role from Phase 1.
- Confirm the printing batch list needs to be exportable (PDF/print) rather than just an on-screen table.

### 6. Estimated timeline
**1–2 weeks** with manual courier tracking. **+1 week** if integrating a courier tracking API.

## PHASE 4 — Academic: Progress, Attendance, Doubts, Live Sessions

### 1. Workflow
This phase is two very different things bundled together — one is a data sync (cheap), the other is two ground-up builds (expensive). Splitting them out matters for scoping:

**A. Progress & online attendance (sync only, built on Phase 2's pipeline):**
```
Frappe LMS Course Progress / Live Class Participant (joined_at, left_at)
        ↓ (extend syncLmsProgress from Phase 2)
students/{id}.lms.progressPercent, .liveSessionsAttended synced into Firestore
        ↓
Shown on Master Student Profile
```

**B. In-person attendance (new, simple):**
```
Staff opens a batch's class roster for a given date
        ↓
Marks Present/Absent per student
        ↓
Attendance % rolls up into student profile
```

**C. Doubt-solving system (new, the largest build in this phase):**
```
Student selects Course → Module → Lesson → writes question, attaches image/PDF/floor plan
        ↓
Doubt ID auto-generated (DVT-00482), status: Submitted
        ↓
Faculty sees it in a doubt queue → status: Under Review
        ↓
Faculty answers → status: Answered
        ↓
Student/staff can close it → status: Closed
        ↓
Full Q&A history visible on Master Student Profile (synced count: Total/Pending/Answered)
```

### 2. Key open decision before this phase can be scoped precisely
**Where does the Doubt system (and any student-facing UI) live — inside Frappe LMS, or inside Homa Booking?**
- Frappe LMS already has Users, file attachments, and course/lesson context, and students are already logged in there while studying — a custom `LMS Doubt` doctype fits naturally and reuses Frappe's file storage.
- Homa Booking today is **admin-only** — there is no student login/dashboard at all. Building the doubt system here means building a first student-facing portal from scratch (auth, mobile-friendly UI), which is a much bigger lift than adding one doctype to an app you already run.
- **Recommendation:** build the Doubt system as a Frappe LMS custom doctype + portal page, and have Homa Booking only pull summary counts (Total/Pending/Answered) into the Master Student Profile via API, the same pattern as progress sync. This avoids duplicating a student-auth system. Needs your confirmation before Phase 4 starts, since it changes which app faculty and students actually use day to day.

### 3. New database structure (assuming the recommendation above)

**`attendance` (new Firestore collection, in-person only):**
| Field | Type | Notes |
|---|---|---|
| studentId, batch | string | |
| date, session | date/string | |
| status | string | `present` \| `absent` |
| markedBy | string | staff uid |

**`students/{id}.doubts` (new nested object, synced from Frappe, read-only in Homa Booking):**
| Field | Type | Notes |
|---|---|---|
| total, pending, answered | number | counts synced periodically |

### 4. Features included
- In-person attendance marking screen per batch/date, roll-up % on Master Profile.
- Doubt submission + faculty answer queue (in Frappe LMS, per the recommendation).
- Live session schedule already exists in Frappe LMS — Homa Booking surfaces upcoming sessions + attended/absent counts on the Master Profile (sync only).

### 5. What gets automated
- Progress and live-session attendance sync — automatic, scheduled (extends Phase 2's job).
- Doubt counts sync — automatic, scheduled.
- Attendance % calculation — automatic on each mark-attendance action.
- Doubt submission → faculty notification — can be automated via Frappe's own notification system.

### 6. What we need from you before starting
- **Decision above: Doubt system hosted in Frappe LMS vs. Homa Booking.**
- Confirm in-person attendance is only needed for offline/classroom batches (online batches are already covered by Live Class Participant data).
- Confirm which staff role (faculty) needs the doubt queue — ties to Phase 1 roles.

### 7. Estimated timeline
**3–5 weeks** — almost entirely driven by the Doubt system build; progress/attendance sync alone would be under a week.

## PHASE 5 — Exams & Certificates

### 1. Workflow
Frappe LMS already runs a complete exam/certificate engine (`LMS Quiz`, `LMS Quiz Submission`, `LMS Assignment Submission`, `LMS Certificate`) — this phase is sync and surfacing, not building an exam system.

```
Student takes quiz/exam in Frappe LMS (existing feature)
        ↓
Score/pass-fail recorded in LMS Quiz Submission (existing)
        ↓ (extend syncLmsProgress from Phase 2)
students/{id}.exam synced into Firestore
        ↓
Certificate eligibility/status shown on Master Student Profile
        ↓
If certificates are physical (printed + couriered) → feeds into Phase 3's notesOrders pipeline
If certificates are digital-only → student downloads directly from Frappe LMS, Homa Booking just shows status
```

### 2. Key open decision
**Are certificates physical (printed and couriered like notes) or digital-only (downloaded from the LMS)?** This determines whether "Certificate: Delivered" status is tracked here or simply reuses the Phase 3 courier pipeline.

### 3. New database structure

**`students/{id}.exam` (new nested object, synced from Frappe):**
| Field | Type | Notes |
|---|---|---|
| quizResults | array | score, percentage, pass/fail per quiz, from `LMS Quiz Submission` |
| certificateStatus | string | `not_eligible` \| `eligible` \| `generated` \| `delivered` |
| certificateUrl | string | link to Frappe-generated certificate, if digital |

### 4. Features included
- Exam/quiz results shown on Master Student Profile (read-only, sourced from Frappe).
- Certificate status pipeline, with "Delivered" hooking into Phase 3 courier tracking if physical.

### 5. What gets automated
- Result and certificate-status sync — scheduled, extends Phase 2/4's sync job.
- If physical: certificate-generated event auto-creates a `notesOrders` entry (reusing Phase 3 automation).

### 6. What we need from you before starting
- **Decision above: physical vs. digital certificates.**
- Confirm certificate eligibility rules (e.g., min. quiz score + attendance %) are already configured correctly in Frappe LMS, or need adjusting.

### 7. Estimated timeline
**1–2 weeks** for sync + status UI. **+1–2 weeks** if physical certificate dispatch needs to be wired into Phase 3.

## PHASE 6 — Automation & Reporting

### 1. Workflow
This phase ties together every Cloud Function trigger built in Phases 1–5 into one coherent chain, and adds the admin-facing reporting layer:

```
Payment Verified → Admission Confirmed → Student ID (exists) → LMS Account Created (Ph.2)
   → Course Assigned (Ph.2) → Welcome Message (Ph.2) → Notes Order Created (Ph.3)
   → Student Added to Batch (Ph.2) → [ongoing] Progress/Doubt/Exam sync (Ph.4/5)
```
Phase 6's job is to end-to-end test this chain fires correctly with zero manual steps, plus build the reporting layer on top.

### 2. New pieces
- **Admin Dashboard home screen** — real-time stat tiles: Total Students, Active Students, New Admissions, Payment Pending, LMS Activation Pending, Notes Pending, Printing Pending, Dispatch Pending, Unanswered Doubts, Upcoming Sessions. Backed by a scheduled Cloud Function that precomputes counts into a single `dashboardStats` document (avoids expensive live aggregation queries on every page load).
- **WhatsApp template library** — extends the existing MSG91 integration (already used for walk-ins/confirmations/reminders) with: Admission confirmation, Payment confirmation, LMS activation, App installation, Course access, Notes ready, Notes dispatched, Doubt session reminder, Payment reminder, Exam notification, Certificate notification.
- **Search & filter** — Student Name, Mobile, Student ID, Course, Batch, Payment Status, Notes Status, LMS Status. Firestore composite indexes cover this for hundreds of students; if the institute scales into the thousands with complex free-text search needs, a dedicated search service (e.g. Algolia) would be a separate, additional cost.

### 3. What gets automated
- The entire admission-to-batch-assignment chain runs without manual staff intervention once payment is marked Paid.
- Dashboard stats refresh automatically (scheduled, e.g. every 15 minutes or on relevant writes).
- All new WhatsApp templates fire on their respective status transitions.

### 4. What we need from you before starting
- Final wording/sign-off on each new WhatsApp template — **each template requires separate approval from Meta/MSG91**, which typically takes a few days per template and is outside our control. Recommend submitting templates for approval as soon as the wording is finalized, in parallel with earlier phases, so approval isn't a bottleneck at the end.
- Confirm expected student volume (hundreds vs. thousands) to decide if Firestore's native search/filtering is sufficient or a dedicated search service is worth the added cost.

### 5. Estimated timeline
**2 weeks of build**, plus external lead time for WhatsApp template approvals (runs in parallel, doesn't block other dev work).
